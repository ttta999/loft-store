# Автоматическое локальное время — результат

16 ноября 2026. Требования включены в основное ТЗ и [отдельный актуальный раздел](local-time-spec.md).

## Что изменено

- В клиенте и админке применяется общий механизм форматирования абсолютных дат для RU/UZ через часовой пояс устройства. Он охватывает заказы, спецзаказы, возвраты, историю, уведомления, рассылки, обновление настроек и аналитику. Группировка аналитики и её кэш также учитывают локальные сутки.
- При смене зоны и возвращении в приложение подписи дат обновляются. Не запрашиваются геолокация, GPS, IP или разрешения местоположения.
- Ручное поле часового пояса удалено. Рабочие часы и серверные напоминания закреплены за `Asia/Tashkent`, добавлена подпись «По времени Узбекистана».
- Планирование рассылки использует местное время менеджера, с подписью «По вашему местному времени». Клиент сохраняет выбранный момент в UTC и передаёт ISO с `Z`. При смене зоны меняется подпись, а не момент отправки.
- Несуществующий час весеннего перехода DST отклоняется; при повторном осеннем часе используется первое вхождение по правилам браузера.
- Применена миграция `20261116133217_local_device_time_and_utc_campaigns.sql`. Сохранены проверки доступа, версии записей, подтверждение аудитории и совместимость со старым форматом планирования. Исторические timestamps, Cron и очереди не пересчитывались; PostgreSQL остаётся в UTC.

## Проверки

- Модульные проверки: клиент 74, админка 16 — пройдены; production-сборки обоих приложений успешны.
- Все локальные проверки базы пройдены, включая UTC-планирование из разных часовых поясов SQL-сессии, неизменность ранее запланированной кампании и независимость рабочих часов от страны менеджера.
- Браузерные проверки охватывают Ташкент, Ригу, Нью-Йорк и смену зоны на Гонолулу; проверены RU/UZ, граница суток, летнее/зимнее время и передача UTC на сервер.
- Полная регрессия: 522 успешных сценария, два сбоя при первом прогоне, один намеренный пропуск. Повторная проверка обоих файлов со сбоями: 33 сценария пройдены. В тесте кэширования добавлено ожидание первоначальной синхронизации ревизии. Сценарий спецзаказа повторно проверен без изменения продуктовой логики.
- Пропущена только живая смена зоны через Chromium CDP в WebKit: этот API там отсутствует. Отдельные контексты с разными зонами проверены и в WebKit. Физический iPhone не использовался.
- В рабочей базе на момент миграции не было запланированных кампаний; сохранность существующего расписания проверена на предварительно созданной записи в изолированной базе. Реальные рассылки и сообщения для тестов не отправлялись.
- Проверки безопасности Supabase не выявили новых замечаний относительно состояния перед миграцией.
