# Обычные заказы и ручные возвраты

Реализация для магазина и административной панели, ноябрь 2026.

## Оформление и статусы

Внутренние значения обычных заказов сохранены. Единый модуль `src/lib/orderState.ts` в обоих репозиториях переводит их в пользовательские названия. `Ожидает оплаты` + отправленный чек + pending означает **На обработке**; `В обработке` означает **Собирается**.

- Самовывоз с оплатой на месте: Принят → Собирается → Готов к выдаче → Получен. Последнее действие требует подтверждения менеджером получения денег и фиксирует paid_at, сумму и валюту.
- Предоплаченный самовывоз: чек → На обработке → подтверждение поступления менеджером → Принят → Собирается → Готов к выдаче → Получен.
- Предоплаченная доставка: чек → На обработке → подтверждение поступления → Принят → Собирается → Упакован → Передан курьеру → Доставлен. Трек остаётся необязательным.

Сервер разрешает только следующий этап. Скриншот не подтверждает оплату. Открытие реквизитов создаёт скрытое незавершённое оформление; его отмена освобождает резерв без возврата и уведомлений. После отправки чека заказ **не истекает автоматически как черновик** и требует решения менеджера. Это осознанное изменение прежнего правила 24 часов.

## Отмена

Клиент обычного заказа может отменить его на проверке оплаты или в статусе Принят. Дальше используется поддержка. Оплаченные спецзаказы клиент самостоятельно не отменяет. Полученный/доставленный заказ нельзя отменять этим процессом.

Менеджер указывает обязательную причину в отдельном окне. После передачи курьеру или закупки спецзаказа требуется ручное согласование с явным подтверждением. Система не отменяет закупку или банковскую операцию автоматически.

Источник client/store/system назначает сервер. Старым отменам источник не приписывается. Отмена, освобождение остатков, запись возврата и постановка сообщения в очередь выполняются одной транзакцией под блокировками клиента и заказа. Повторный запрос не освобождает остатки второй раз.

## Возвраты

`refunds` содержит единственную запись на заказ (UNIQUE order_id), снимок исходной суммы и отдельно фактически полученную сумму/валюту. Основной заказ остаётся отменённым.

- Неоплаченный заказ с оплатой при получении: активный возврат не создаётся.
- Чек без подтверждённого поступления: **Проверка платежа**, сумма не обещается.
- Подтверждённая оплата: **Ожидает возврата**, берётся сохранённая фактическая оплата; для достоверных старых записей — сумма заказа и сохранённый курс.
- Проверка → Оплата поступила: менеджер вводит фактическую сумму и валюту. Заказ не возобновляется.
- Проверка → Оплата не поступила: **Возврат не требуется**. Позже запись можно повторно рассмотреть с обязательной причиной; новая финансовая запись не создаётся.
- Ожидает возврата → **Возврат выполнен**: перевод через банк выполняется вручную; затем менеджер загружает квитанцию, ставит подтверждение и подтверждает действие в модальном окне.

Перед финансовыми действиями менеджер берёт возврат в работу. Закрепление постоянно, без автоматического истечения: другой менеджер не может начать или завершить перевод по этой записи. Изменения проверяются сервером под блокировками; ключ запроса сверяется с его содержимым. Повторное завершение не создаёт вторую операцию. История `private.store_refund_audit` сохраняет автора, действие, время и состояния до/после. Первоначальная оплата, чек, paid_at и сумма заказа сохраняются.

В админке есть карточка Возвраты со счётчиком активных записей, список, фильтры, поиск, история, защищённые документы, переход к заказу и ручное сообщение клиенту. Обновление возврата сбрасывает зависимые кэши. Новые активные возвраты также появляются в колокольчике.

## Telegram и деньги

Новые обычные шаблоны находятся в `server/orderNotifications.ts`. Сервер сохраняет снимок этапа, суммы, валюты и трека в существующей очереди; интерфейс не отправляет вторую копию статусного сообщения. Ключ события стабилен. Для одного заказа клиентские финансовые события выдаются по порядку; повторные обработки используют существующие lease/retry/complete.

Отмена с возвратом объединена в одно сообщение; результат проверки или завершение возврата отправляется отдельным последующим событием. Менеджер получает клиентскую отмену отдельным событием. HTML пользовательских значений экранируется. После чека повторное предложение оплатить спецзаказ исключено. Остальные согласованные шаблоны спецзаказов сохранены.

USD и UZS отображаются по валюте заказа/фактической оплаты. История не пересчитывается по текущему курсу. Неизвестная сумма помечается для проверки, а не превращается в ноль или вымышленную сумму.

## Безопасность

- Авторизация и MFA менеджеров сохранены на всех новых RPC. Прямые финансовые INSERT/UPDATE/DELETE для authenticated запрещены.
- Клиентский API получает возвраты только для удостоверенного пользователя и возвращённых ему заказов. Явная проекция исключает внутренние комментарии, audit, назначенного менеджера и документы возврата.
- Таблицы защищены RLS. Аудит расположен в private без клиентских политик; отсутствие политик здесь означает намеренный запрет доступа, а не открытый доступ.
- Bucket refund-proofs приватный. Upload только менеджером, за которым закреплён ожидающий возврат; путь содержит ID возврата и auth.uid. Объект нельзя перезаписать или удалить обычным менеджером. Сервер проверяет владельца, путь, существование, MIME и размер перед прикреплением.
- Разрешены JPEG/PNG/WebP/PDF до 8 МБ. Админка получает короткоживущие подписанные ссылки. Клиенту квитанция обратного перевода не раскрывается, чтобы не показывать банковские данные третьих лиц.
- Черновики скрыты в клиентском API и ограничительной политике админки; отдельный MFA RPC позволяет менеджеру проверить поздний перевод даже по скрытому оформлению.
- Сервисные ключи и токены остаются на сервере.

## Миграция и совместимость

Новая миграция `20261112120358_order_refunds.sql` добавляет таблицы/поля/RPC/политики и точечно заменяет функции оплаты, отмены и очереди. Применённые предыдущие миграции не редактируются.

Исторические refund_pending получают связанную запись без повторного обязательства и без рассылки старых событий. При неоднозначной сумме используется Проверка платежа. Исторический источник отмены не придумывается.

Пять статусов исходной заявки, отдельная корзина, запрет смешивания/нескольких спецзаказов, полная предоплата, международная цепочка и связь заявки с оформленным заказом сохранены. Отмена не возвращает уже оформленную заявку в Оценён.

## Ограничения

Банковской интеграции нет: приложение фиксирует подтверждение менеджера и квитанцию, но не проверяет движение денег в банке. Перед повторным действием после сетевой ошибки нужно сверить банковский перевод. Закрепление за менеджером само не истекает; аварийная передача другому ответственному требует отдельного контролируемого решения, а не автоматического таймера.

Частичные возвраты и возврат полученного товара не входят в эту версию. Реквизиты клиента не собираются формой и не хранятся в публичных полях. Админка остаётся русскоязычной как раньше; новые клиентские состояния и пояснения поддерживают русский и узбекский.

Очередь предотвращает повторную обработку сохранённых событий. Как и любой Telegram sendMessage без банковской/провайдерской идемпотентности, при неоднозначном сетевом исходе после приёма сообщения Telegram абсолютная гарантия exactly-once невозможна; повторный банковский перевод система автоматически не инициирует.

## Применение и технические результаты

Миграция `20261112120358_order_refunds.sql` применена к проекту Supabase `kmbmsbydxnxxiwypaxwm`. После применения: 6 существующих заказов и 3 исходные заявки сохранены, создано ровно 3 связанных исторических возврата Ожидает возврата. Источники старых отмен остались NULL, очередь новых исторических уведомлений пуста.

Сборки обоих репозиториев проходят. Unit: магазин 52/52, админка 11/11. SQL проверки возвратов, специальной поставки и архитектуры безопасности проходят с полным откатом тестовых данных. Отказ второму MFA-менеджеру проверен последовательными вызовами под разными сессиями. Независимый одновременный нагрузочный тест двух RPC не выполнен: MCP не дал надёжно наблюдать перекрытие запросов, а отдельный CLI не авторизован. Серверная сериализация обеспечивается общим advisory lock клиента, блокировками строк заказа/возврата, UNIQUE order_id и проверкой ответственного менеджера; это ограничение тестового окружения не заменяется утверждением о прошедшем конкурентном нагрузочном тесте.

Security advisors: новых открытых таблиц или анонимных финансовых функций нет. Добавилось намеренное отсутствие клиентских политик у private-аудита (deny-by-default) и 5 предупреждений о доступных authenticated SECURITY DEFINER RPC — каждый из этих RPC проверяет действующую административную сессию и MFA. Старые 2 предупреждения об анонимных функциях не изменились. Проверка утёкших паролей остаётся ограничением текущего тарифа Supabase, ранее подтверждённым владельцем.

Справка Supabase по предупреждениям: [RLS без политик](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy), [SECURITY DEFINER](https://supabase.com/docs/guides/database/functions#security-definer-vs-invoker), [защита паролей](https://supabase.com/docs/guides/auth/password-security).

Итоговый полный браузерный прогон mobile Chrome: **130/130 passed**. Новый раздел возвратов отдельно проверен в mobile Chrome, desktop Chrome и WebKit: **9/9 passed**. Сборки обеих систем успешны; предупреждение Vite о существующем основном JS chunk >500 kB остаётся и не является ошибкой сборки.
